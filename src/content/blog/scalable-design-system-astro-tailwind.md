Every site starts with a handful of pages and a few shared styles. Then the marketing pages arrive, then the blog, then the case studies, then the pricing page — and suddenly the same button exists in five slightly different shades, the spacing between sections varies by page, and changing the brand colour means editing dozens of files. A design system is the answer to that drift: a single source of truth for colour, typography, spacing, and components, so that every page is built from the same parts and a change in one place reaches the whole site.

This guide shows how to build that system with Astro and Tailwind CSS, grounded in how this site actually does it: Tailwind v4's CSS-first configuration, design tokens generated from a single theme file, shared component styles, and Astro components that carry the semantics as well as the appearance. The goal is not a component library for its own sake — it is a site where adding the hundredth page is exactly as much design work as adding the first.

## What a Design System Is (and Is Not)

A design system has three layers, and confusing them is the most common mistake in building one.

The bottom layer is **tokens**: named values for colour, type, spacing, radius, and shadow. A token is a decision with a name — `--color-primary: #8F2FFE` means "the brand violet", and every use of that violet goes through the token. Tokens are the only place raw values live.

The middle layer is **components**: reusable pieces built from tokens. A button, a card, a section header, a badge. A component decides its own spacing, typography, and colour by referencing tokens, so it looks right wherever it is used and changes everywhere at once when a token changes.

The top layer is **patterns**: compositions of components into pages — a hero section, a pricing table, a blog listing. Patterns are built in Astro pages and layouts from the components below them, and they are where the site's actual design lives.

What a design system is not is a pile of utility classes copied between pages. Tailwind's utilities are the raw material, not the system. The system is the tokens and components that sit on top of them and give the utilities meaning. A page that writes `bg-[#8F2FFE] text-white px-6 py-3 rounded-xl` has hardcoded a button; a page that writes `<Button variant="primary">` has used a design system. The difference shows up the first time the brand colour changes.

## Tokens: One Source of Truth

Tokens live in one place and are generated, not hand-written in two places. On this site, the source of truth is `src/config/theme.json`:

```json
{
  "colors": {
    "default": {
      "theme_color": {
        "primary": "#8F2FFE",
        "secondary": "#DF53FE",
        "primary-dark": "#1A131F",
        "body": "#0E0912",
        "border": "#FFFFFF",
        "light": "#fff",
        "gray": "#B9B7BA",
        "dark": "#121212",
        "dark_gray": "#292929",
        "card": "#151019"
      },
      "text_color": {
        "text": "#ffffff",
        "text_dark": "#040404",
        "text_light": "#f7f7f7"
      }
    }
  },
  "fonts": {
    "font_family": {
      "primary": "Inter:wght@300;400;500;600",
      "primary_type": "sans-serif"
    },
    "font_size": { "base": "16", "scale": "1.2" }
  }
}
```

A generator script (`scripts/themeGenerator.js`) turns that file into `src/styles/generated-theme.css`, which Tailwind v4 reads as `@theme` tokens:

```css
/**
 * Auto-generated from "src/config/theme.json"
 * DO NOT EDIT THIS FILE MANUALLY
 * Run: node scripts/themeGenerator.js
 */

@theme {
  /* === Colors === */
  --color-primary: #8f2ffe;
  --color-secondary: #df53fe;
  --color-primary-dark: #1a131f;
  --color-body: #0e0912;
  --color-border: #ffffff;
  --color-light: #fff;
  --color-gray: #b9b7ba;
  --color-dark: #121212;
  --color-dark-gray: #292929;
  --color-card: #151019;
  --color-text: #ffffff;
  --color-text-dark: #040404;
  --color-text-light: #f7f7f7;

  /* === Font Families === */
  --font-primary: Inter, sans-serif;

  /* === Font Sizes === */
  --text-base: 16px;
  --text-base-sm: 12.8px;
  --text-h6: 1.2rem;
  --text-h6-sm: 1.08rem;
  --text-h5: 1.44rem;
  --text-h5-sm: 1.296rem;
  --text-h4: 1.728rem;
  --text-h4-sm: 1.5552rem;
  --text-h3: 2.0736rem;
  --text-h3-sm: 1.86624rem;
  --text-h2: 2.48832rem;
  --text-h2-sm: 2.239488rem;
  --text-h1: 2.9859839999999997rem;
  --text-h1-sm: 2.6873856rem;
}
```

The chain matters more than any single value. The JSON file is the editable source: a designer changes a colour there, runs the generator, and the CSS tokens update. The generated file carries a "do not edit manually" header — hand-edits to generated output are silently overwritten on the next run. And the tokens are Tailwind v4 `@theme` variables, so they become utilities automatically: `--color-primary` gives you `bg-primary`, `text-primary`, and `border-primary` with no further configuration.

That last point is the Tailwind v4 difference. There is no `tailwind.config.js` on this site — Tailwind 4.3.5 is configured in CSS, not JavaScript. The entry stylesheet, `src/styles/main.css`, is the configuration:

```css
@import "tailwindcss";
@plugin "@tailwindcss/forms";
@plugin "@tailwindcss/typography";

/* Auto-generated theme from "theme.json" */
@import "./generated-theme.css";

@import "./safe.css";
@import "./utilities.css";

@layer base {
  @import "./base.css";
}

@layer components {
  @import "./components.css";
  @import "./navigation.css";
  @import "./buttons.css";
}
```

The import order is the architecture: Tailwind first, then the generated tokens, then the layers of custom styles. If you are coming from Tailwind v3, the shift is that the config file is gone and the CSS file is the config — tokens, plugins, and custom layers all live here.

## Colour Tokens: Semantic Names, Not Paint Swatches

The colour tokens on this site are named by role, not by appearance, and that distinction is what makes them scale. `primary` is the brand violet; `body` is the page background; `card` is the surface cards sit on; `text` is the default text colour. A component that needs a card background writes `bg-card`, not `bg-[#151019]`. When the card colour changes, every card changes — and the name still makes sense, because the name describes the role.

A few rules keep colour tokens honest. Never add a token for a single use: if a colour appears once, it is a one-off value, not a token, and giving it a name pretends otherwise. Keep the palette small: this site has ten theme colours and three text colours, which is enough for a whole site and few enough to hold in your head. And name tokens for what they are for, not what they look like — `primary` survives a rebrand, `purple` does not. The one exception is the raw brand colour itself, which is allowed to be a literal value in the token file, because the token file is where literals live.

Dark mode deserves a note here. This site is dark by default — the body background is near-black (`#0E0912`) and the text is white — so there is no light theme to toggle. If your system needs both, define the tokens per theme rather than per colour: the same `--color-body` token resolves to a dark value in one theme and a light value in another, and every component stays unchanged. The component never knows which theme is active; it only knows the token name.

## Typography Tokens: A Scale, Not a List

Typography is a scale, not a collection of font sizes chosen per page. This site's scale is generated from a base of 16px and a ratio of 1.2: each step up multiplies by 1.2, producing a harmonious progression from body text through six heading levels. The generated tokens make the scale concrete — `--text-h1` is roughly 3rem, `--text-h2` roughly 2.5rem, down to `--text-h6` at 1.2rem — and each level has a smaller variant (the `-sm` tokens) for narrow screens.

The scale does two jobs at once. It makes headings consistent — every `<h2>` uses the same token, so the visual hierarchy is the same on every page — and it makes responsive typography mechanical: the small variant is defined alongside the large one, so a heading that is too big on mobile is fixed by the token, not by a one-off override.

The font family is a single token too: `--font-primary: Inter, sans-serif`. One family, four weights (300, 400, 500, 600), used everywhere. A design system with three font families and six weights is not expressive; it is inconsistent, and the inconsistency shows up as pages that feel like they belong to different sites.

The practical rule for typography tokens is to define the scale once and forbid raw font sizes in components. A component that writes `text-[22px]` has opted out of the system. A component that writes `text-h4` is participating in it, and when the scale changes, it changes with everything else.

## Spacing and Layout Tokens

Spacing is the quiet part of a design system and the part where drift is most visible. Two sections with slightly different vertical padding look like a mistake, even if no visitor can name the difference. The fix is the same as for colour: tokens and shared classes, not per-page values.

This site's shared layout styles live in `src/styles/components.css`, and the section and container classes show the pattern:

```css
/* section style */
.section {
  @apply py-24 xl:py-28;
}

.section-sm {
  @apply py-16 xl:py-20;
}

/* container */
.container {
  @apply mx-auto xl:max-w-325! px-4;
}
```

A section is `.section` or `.section-sm` — two sizes, used everywhere, with the responsive step built in. A container is `.container` — centred, with a maximum width and horizontal padding. No page invents its own section padding or its own container width, so no page can drift from the rhythm. The `@apply` directive is Tailwind's way of composing utilities into a named class, and it is the right tool here: the class is the token, and the utilities are its definition.

The same discipline applies to the smaller spacings. Cards, buttons, and form fields use the spacing scale (multiples of the base unit) rather than arbitrary pixel values. The result is a site where the gaps feel regular because they are regular — every gap is a value from the same scale, and the eye reads that regularity as polish.

## Components: Tokens Made Concrete

Components are where tokens become visible. This site's component library lives in `src/layouts/components/` — Astro components for the static parts, React components (`.tsx`) for the interactive ones — and each component is built from tokens and shared classes rather than raw values.

The blog card shows the pattern clearly:

```astro
<article class="bg-card/70 border border-border/6 rounded-3xl overflow-hidden w-full flex flex-col gap-0 group relative">
  <div class="p-2.5">
    <div class="rounded-3xl overflow-hidden bg-dark/10 w-full aspect-1150/600 relative">
      <!-- feature image -->
    </div>
  </div>
  <div class="px-5 pt-4 pb-5 flex flex-col gap-3 relative z-2">
    <!-- title, meta, excerpt -->
  </div>
</article>
```

Every value in that markup is a token or a scale step: `bg-card` for the surface, `border-border` for the edge, `rounded-3xl` for the radius, `p-2.5` and `px-5` from the spacing scale. Nothing is a hex code, nothing is an arbitrary pixel value. If the card colour changes, the card changes; if the radius scale changes, every card changes with it. The component is also semantic — an `<article>` — and it carries its interactive behaviour (the hover state on the `group` class) as part of its definition, not as a page-level addition.

Buttons follow the same pattern in `src/styles/buttons.css`:

```css
.btn-primary {
  @apply border-primary bg-gradient-button text-white hover:brightness-110 hover:!text-text transition duration-300;
}

.btn-outline-primary {
  @apply border-primary text-primary hover:bg-primary hover:text-white transition duration-300;
}
```

Two variants, defined once, used everywhere. A page never writes its own button styles; it picks a variant. That is the whole contract of a component system: the page decides which component and which variant, and the component decides how it looks.

The component rules that make this scale are few. A component takes props for content and variant, not for styling — `variant="primary"` is a prop, `class="bg-purple-600"` passed from a page is a leak. A component never reaches outside its own definition for a colour or a size. And a component carries its accessibility with it: the button is a real `<button>`, the card is an `<article>`, the navigation is a `<nav>`. The [accessibility guide](/blog/web-accessibility-astro-guide) covers why that matters — a design system that bakes in semantics gives every page accessibility for free, while one that leaves it to each page guarantees that some page will forget.

## Variants Without Explosion

A component with two variants is a system. A component with twenty is a mess that happens to be organised. Variants should cover the real states a component has — primary and outline for a button, small and large for a badge — and stop there. Each new variant is a new visual language the site has to maintain, and variants multiply: two button styles times three sizes times two states is twelve combinations to test and to keep consistent.

The discipline is to add a variant only when a page genuinely needs a look the existing variants cannot express, and to ask first whether the page needs a different component instead. A "large primary button with an icon" is a variant of the button. A "card that acts as a link" is a different component from a card, because its semantics and keyboard behaviour are different.

Composition beats configuration for the same reason. A card component that accepts a header, a body, and a footer as slots is more flexible than a card with twelve props controlling every part — and it stays readable, because the page shows the structure instead of hiding it behind prop names. Astro's `<slot />` makes this natural: the component defines the frame, the page supplies the content.

## Theme Management: Changing the System

A design system earns its keep when the theme changes. The workflow on this site is deliberately mechanical: edit `theme.json`, run the generator, and the tokens update. No component changes, no page changes, no search-and-replace through the codebase. That is the test of whether the system is real — if changing the brand colour requires editing components, the tokens are decoration.

Theme management also means knowing what not to change by hand. The generated CSS file is output, not source. The theme JSON is source. The generator script is the bridge, and it is the only thing allowed to write the generated file.

For sites that need more than one theme — a light and a dark mode, or a white-label variant per customer — the same structure extends: the token names stay fixed, and the values behind them change per theme. The components never branch on the theme, because they only ever reference token names. The theme is a data problem, not a component problem, and keeping it that way is what makes multiple themes affordable.

## Documentation and Adoption

A design system nobody uses is a style guide, not a system. Adoption comes from making the system the easiest way to build a page. When a developer reaches for a button, the component should be closer than writing the classes by hand — imported from the shared components folder, documented with its variants, and visible in the codebase's own pages as the example to copy.

Documentation for a system of this size does not need a separate site. The token file is documented by its own structure, each component carries its variants in its props, and the pages of the site itself are the showcase: the blog listing demonstrates the card, the pricing page the pricing components, the homepage the hero and section patterns. A new page is built by copying an existing page and changing the content, which is the fastest documentation of all.

The adoption rule that matters most is the negative one: do not allow one-off styles in pages. A page that writes its own colours or spacing has opted out of the system, and one opt-out invites the next. Code review should catch it the way it catches any other deviation from the shared pattern — not as a style preference, but as a defect, because the drift it causes is real and cumulative.

## Common Mistakes

**Hardcoding values in components.** A hex code in a component is a token that was never made. Every literal value in a component is a future search-and-replace.

**Editing generated files.** The generated theme CSS is output. Edit `theme.json` and regenerate. Hand-edits are lost on the next run.

**Too many variants.** Each variant is a commitment. Two or three per component is a system; twenty is a catalogue nobody can hold in their head.

**Tokens named by appearance.** `purple` breaks on rebrand; `primary` survives it. Name tokens by role.

**Letting pages invent spacing.** Section padding, container width, and card gaps belong to shared classes. A page that invents its own has drifted, even if it looks fine alone.

**Forgetting the responsive step.** Every token that affects size needs its small-screen behaviour defined alongside it, not discovered later on a phone.

**Building the system before the site.** Tokens for colours nobody uses and components for pages that do not exist are speculative work. Build the tokens the current pages need, and add the rest when a page demands them.

## Frequently Asked Questions

**Do I need a design system for a small site?**
Yes, at this site's scale — tokens and a handful of shared components. The cost is a theme file and a components folder; the benefit is that the tenth page looks like the first. A small site is where a system is cheapest to build and where drift starts.

**Should tokens live in JSON or in CSS?**
Either, as long as there is one source. This site keeps the source in JSON and generates CSS from it, which suits a workflow where designers edit the JSON. If only developers edit the tokens, defining them directly in `@theme` is equally valid.

**How is Tailwind v4 different from v3 for design systems?**
Tailwind v4 is CSS-first: there is no JavaScript config file, and tokens are defined with `@theme` in CSS. The utilities are generated from the tokens the same way, but the configuration lives in the stylesheet. The earlier [Tailwind CSS post](/blog/post-13) covers what changed in v4, and the [responsive design guide](/blog/responsive-websites-tailwind-css-guide) shows how the same tokens drive responsive layouts. The [islands architecture guide](/blog/astro-islands-architecture-partial-hydration) covers when a component needs to be interactive, which decides whether it is an Astro component or a React one.

**How many components should a system have?**
As many as the site uses, and no more. Start with the components the current pages need — button, card, section header, badge, navigation — and add one when a page needs a new pattern.

**Can a design system include accessibility?**
It should. A component that is a real `<button>` with visible focus and a real `<article>` with a proper heading gives every page those behaviours for free. Accessibility baked into components scales; left to each page, it does not.

**When should a component be React instead of Astro?**
When it needs client-side interactivity — state, event handling, script-driven animation. Static components are Astro; interactive ones are React islands. The split keeps shipped JavaScript minimal while the design system stays unified.

## Conclusion

A scalable design system is a short chain with no weak links: one theme file, generated tokens, shared component styles, and Astro components built from those tokens. Change the theme file and the whole site follows; add a page and it is built from parts that already exist; fix a component and every page inherits the fix. The system is not the components themselves — it is the rule that raw values live in exactly one place, and everything else references them by name.

Start with the tokens your current pages need, generate them from a single source, and build the components those pages already repeat. The system will grow with the site, and the site will stop drifting.
